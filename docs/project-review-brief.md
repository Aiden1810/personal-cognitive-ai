## 3. 产品定位与核心问题

一句话定义：**知衡通过日常对话和用户提供的经历，形成带原话依据、可由用户修正的当前画像；用户自行设定希望保持或改变的方向，AI 在后续对话中参考两者提供帮助。**

项目关注的是：AI 的建议能否考虑用户的实际背景、已有行为和自主目标；当 AI 对用户的理解不准确时，用户能否看见依据并纠正。

产品的几个关键区分：

1. **AI 候选洞察**是待审核推测；**当前画像**是用户已确认且来源有效的记录。用户确认也不等于经过科学验证的客观事实。
2. **当前画像**描述已有资料；**目标画像**描述用户希望前进的方向，修改目标不能把它改写成已经发生的行为。
3. **改变意愿**由用户自行选择；它与目标是否启用分开，不是人格分数、问题严重程度或目标完成率。
4. **应用层记忆更新**依靠保存、审核与选择上下文，不是重新训练或微调基础大模型。

2026 年 9 月 28 日，项目方向已调整为聊天优先。旧方案中的普通 AI、Original Me、Better Me 三视角决策对比只作为历史原型保留，不再是正式软件主流程。

产品方向文档记载：项目参考 Digital Twin v2（`charlesJ721/digital-twin`）的七维资料组织思路，没有直接 Fork 或照搬整套产品；当前也没有接入 Second Me 平台。工作区名称 `second me` 不代表已实现数字分身训练或某个平台集成。

## 4. 七维框架与用户流程

七维用于组织资料，不是心理测评量表，缺少资料时保持未知或“尚待了解”。

| 代码值 | 名称 | 用途 |
| --- | --- | --- |
| `personality` | 人格特质 | 整理有依据的特点与动机，不能由一次事件断言稳定人格 |
| `cognitive_architecture` | 认知架构 | 思考、学习和决策方式 |
| `values_and_beliefs` | 价值观与信念 | 用户重视的事情与判断依据 |
| `behavioral_patterns` | 行为模式 | 经历中出现的行动方式，长期模式需要更多证据 |
| `knowledge_structure` | 知识结构 | 熟悉领域与知识组织方式 |
| `social_relations` | 社会关系 | 合作、互动与建立信任的方式 |
| `narrative_self` | 叙事自我 | 用户如何描述自己以及重要经历 |

当前核心流程如下：

```text
用户正常聊天 → 服务端请求真实模型 → 双方消息保存到浏览器
                    ↓
手动提取，或用户开启后按条件触发提取
                    ↓
最多 3 条候选画像，每条带用户原话来源
                    ↓
用户核对：确认 / 修改后重新审核 / 驳回 / 删除
                    ↓
已确认且来源有效的记录 → 七维当前画像

用户自行填写文字目标 + 可选改变意愿 → 启用或暂停
                    ↓
后续聊天读取相关有效画像与启用目标 → AI 提供针对性帮助

用户实际行动 → 手动记录选择、结果与自评 → 回看记录
```

最后的行动记录已经实现，但反馈自动更新候选画像、调整目标或证明长期改善的完整机制尚未实现。

## 5. 当前页面与功能

### 5.1 路由总览

| 路由 | 内容 | 当前性质 |
| --- | --- | --- |
| `/` | 跳转到 `/chat` | 当前首页入口 |
| `/chat` | 对话列表、真实 AI 聊天、候选提取和审核 | 核心技术原型 |
| `/profile` | 七维当前画像、用户目标、人工整理、AI 观察草稿 | 核心技术原型 |
| `/progress` | 行动选择、观察结果、自评与近期回顾 | 本地反馈工具 |
| `/account` | 邮箱注册登录、备份下载、手动云端备份和恢复 | 已有代码，云端完整流程仍待实测 |
| `/auth/callback` | 验证邮件回调，交换登录会话 | 账户服务端路由 |
| `/history` | 旧案例与行为模式展示 | 合成占位演示 |
| `/goals` | 旧决策方案的目标展示 | 合成占位演示，区别于 `/profile` 的新目标 |
| `/decision` | 旧三视角决策页面 | 输入和结果占位，没有真实三视角生成 |

导航将当前工作区与“旧版决策演示”分开。现有 CSS 采用米白背景、深绿色强调色和文字排版，包含响应式规则、键盘焦点、跳过导航链接及部分 ARIA 状态提示；本轮未进行浏览器视觉或无障碍实测。

### 5.2 聊天

- 可新建、选择和删除对话，保存双方消息，刷新后保留。
- 对话标题取第一条用户消息的前 28 个字符。
- 输入支持 Enter 发送、Shift + Enter 换行，并处理中文输入法组合状态；可复制 AI 回复。
- 每条输入最多 10,000 字符；发送给模型的当前对话窗口最多 30 条双方消息、合计 40,000 字符。完整历史仍保存在本地，超出窗口的旧消息没有自动总结机制。
- 先保存用户消息再请求模型；请求失败时保留输入，显示错误并支持重试，不制造假回复。
- 当前使用普通 JSON 请求和完整文字响应，没有流式输出。
- 发送前读取有效确认画像和启用目标；画像或目标存储损坏时会提示并阻止正常发送，避免错误资料进入上下文。
- 删除对话会尝试清除所有引用该对话的画像洞察与对应自动整理检查点。即使发生跨模块保存失败，后续来源校验也会排除无效洞察。
- 明确清空全部对话会同时清空画像和自动提取检查点；目标、人工整理和行动反馈属于其他数据模块，不等于“一键清空所有项目数据”。

### 5.3 画像候选提取、来源与审核

- 用户可点击“提取近期对话候选”。
- 提取窗口只读取当前对话最近最多 20 条**用户发言**，合计不超过 20,000 字符；助手消息不作为证据，也不占用这个窗口。
- 界面显示实际读取的用户发言数量、总数量及遗漏数量。
- 附带最多 30 条与本批原话相关的已有候选、确认和驳回记录，供模型减少重复；这些记录不能作为新候选的证据。
- 模型最多提出 3 条候选，每条包含维度、描述和来源引用。证据不足时空数组是有效结果。
- 服务端和客户端均检查引用的消息 ID、用户角色与连续原话片段，过滤编造引用、助手引用和不合法结构。
- 候选统一以 `ai_inference`、`candidate` 保存，不能自动确认为事实。
- 用户可确认、修改、驳回、删除。修改后标记为 `user_statement`，重新进入 `candidate`，必须再次确认才能用于聊天。
- 去重结合模型提示与轻量文字正规化；能过滤部分大小写、空白、结尾标点差异，但没有完整的语义去重。
- 删除源对话时，只要一条洞察引用该对话，即使它还有其他来源，当前清理逻辑也会删除整条洞察。

### 5.4 可选持续整理

- 默认关闭，由用户主动开启。
- 开启时把各对话当前最后一条用户发言记为起点；此后同一对话每新增至少 4 条用户发言，在 AI 成功回复并保存后触发提取。
- 使用同一个候选接口与读取上限；可能再次读取窗口内已处理的消息，并依靠已有审核记录减少重复。
- 新结果仍是待审核候选；失败显示提示，处理检查点用于避免重复请求。
- 这是聊天界面触发的整理机制，页面关闭后没有独立后台任务，也没有自动合并长期画像。

### 5.5 七维当前画像与目标

- `/profile` 展示七个维度，并将当前画像与用户方向并排显示。
- 记录分为有效确认、待审核、已驳回、来源失效四组；未知维度不会自动填合成资料或打分。
- 只有确认且全部来源仍有效的洞察进入当前画像；“有效”指原对话和用户消息存在、仍包含引用片段，不代表已经验证描述的语义正确性。
- 每条可查看引用片段与原对话标题；当前画像对象没有单独的创建时间字段，也没有完整审核历史。
- 每个维度最多一个文字目标，最多 500 字符，可修改、暂停、启用和删除。
- 编辑暂停目标时保持暂停，不会悄悄启用。未填写画像的维度也可以设目标，目标不必从已有洞察自动生成。
- 改变意愿可选：暂不想改变、稍微想改变、比较想改变、很想改变、当前最想改变，对应 `not_now / slight / moderate / strong / highest`。
- 每档有文字解释，可清除；旧目标没有这个字段时保持未设置。
- 下一次聊天只发送启用的目标，包括其可选意愿。暂停状态与意愿是两个独立字段。

### 5.6 人工整理与 AI 综合观察

人工整理：

- 用户可把已确认且来源有效的洞察标为“想发挥的优势”或“想改善的地方”。当前每条洞察最多一个此类标记。
- 用户可选择两条不同洞察，写下值得核对的地方，查看双方描述和原话；同一对洞察不能重复加入。
- 标记与核对笔记保存在独立本地模块，不改写原画像，也不直接进入聊天上下文。
- 来源失效、洞察删除或不再确认后，对应整理内容不会作为当前有效内容展示，但部分底层标记可能仍保留。

AI 综合观察：

- 用户主动点击后，发送最多 20 条有效确认画像的描述、维度和原话摘录。
- 当前选择依据是传入画像列表的末 20 条，不是语义检索；该列表由七维总览聚合，不能简单等同于全局最近 20 条。
- 服务端固定请求 `deepseek-flash`，整理可能的优势、改善方向和值得核对的张力，各类最多 3 条。
- 优势与改善方向各引用一条已有洞察；张力必须引用两条不同洞察，未知 ID 会被过滤。
- 草稿仅在当前页面内存中暂存，不写入事实画像、不参与聊天、不随云端快照备份。画像资料变化后旧结果不再显示。
- 当前尚未实现稳定的自动矛盾检测、冲突解决与历史追踪。

### 5.7 行动反馈

- `/progress` 可为一个已有目标记录实际行动、观察结果和用户自评。当前目标列表也包含已暂停目标。
- 自评为三类：更接近目标、暂时看不出变化、与目标有偏差，对应 `toward / unclear / away`，不是数值评分。
- 行动最多 500 字符，结果最多 1,000 字符；本地最多 500 条反馈。
- 每条保存当时目标文字和维度，后续编辑或删除目标不改写旧记录。
- 同一目标 ID 至少有 6 条记录后，比较最近 3 次与之前 3 次的分类数量。数字反映用户填报，不代表系统测出了成长幅度。
- 当前支持新增、查看、删除，没有完整的编辑反馈、定期提醒或反馈驱动画像更新机制。
- 目标编辑保留原 ID，因此近期比较可能混合修改前后的目标内容；旧文本虽有保存，比较尚未按目标版本分组。

## 6. 技术架构和目录

这是一个 Next.js 应用，浏览器 UI、同仓库服务端接口和外部模型服务形成主要链路，没有另建 Python/FastAPI 后端。

```text
React 页面与 feature 组件
  ├─ client Hook → store 函数 → 浏览器 localStorage
  ├─ API 客户端 → Next.js Route Handler → DeepSeek
  └─ Supabase 浏览器客户端 → Auth / user_snapshots

公共类型与数据校验约束每层输入输出
```

`client.ts` 主要把浏览器数据变化接到 React；`store.ts` 负责读取、校验和修改数据；API 模块负责网络调用；页面组合这些模块。这种拆分让核心逻辑可以通过内存存储和模拟请求测试。

## 8. 模型与服务端接口

### 8.1 模型链路

代码调用 `https://api.deepseek.com/chat/completions`。聊天与候选提取默认模型为 `deepseek-flash`，可通过服务端 `LLM_MODEL` 修改；AI 综合观察路由当前固定使用 `deepseek-flash`。

当前代码设置 `thinking: { type: "disabled" }`、`stream: false`；聊天、提取与观察输出上限分别为 1,000、900、1,200 个输出 token。这里的字符窗口与输出 token 上限含义不同。

服务端等待上限 30 秒，客户端请求上限 35 秒。提取和综合观察请求 JSON 结构化结果，检查格式及部分截断情况。

提示词要求模型：参考用户确认资料，保留不确定性；把资料当数据而非系统指令；不诊断、不自动人格打分、不代替用户做最终选择；尊重目标和意愿，低意愿不施压，也不能因此隐瞒事实或一味迎合。当前没有赋予模型执行命令、改文件或向别人发送消息的工具。

### 8.2 三个当前 AI 接口

| 接口 | 输入 | 成功结果 |
| --- | --- | --- |
| `POST /api/chat` | `messages, insights?, goals?` | `{ ok: true, data: { reply } }` |
| `POST /api/profile/extract` | `conversationId, messages, existingInsights?` | `{ ok: true, data: { candidates } }` |
| `POST /api/profile/reflect` | `insights: [{ id, dimension, statement, quotes }]` | `{ ok: true, data: { reflection } }` |

错误通常统一为 `{ ok: false, error: { code, message } }`，包含校验失败、模型未配置/不可用、模型格式无效、来源拒绝或内部失败；对应 400、403、503 或 500 等状态。

接口检查本地 Host 与 Origin，仅允许本地开发来源；**三个 AI 接口在 `NODE_ENV=production` 时直接返回 503**。当前账户代码的存在不会自动解除此限制。

因此：`npm.cmd run build` 可以通过，但 `npm.cmd run start` 的生产模式不会提供可用的 AI 聊天、提取和综合观察。公开上线前还需要把真实账户认证、请求授权、额度或限流和防滥用加到 AI 接口，而不能只删除开关。

### 8.3 画像如何进入回复

1. 浏览器根据对话原文排除来源失效的洞察。
2. 只保留 `confirmed`，按当前问题与描述/证据的文字重合排序，最多发送 20 条。
3. 中文使用相邻两字，英文使用字词进行轻量匹配；同分优先后添加的记录。没有匹配时也会选取后添加记录。
4. 只发送 `active` 目标，并把可选意愿转成统一文字标签和解释。
5. 服务端再次校验形状并筛选确认状态和启用状态，将附加资料放入最后一条用户消息的参考区，配合系统提示词生成回复。

当前不是完整 RAG（检索增强生成）系统，没有 embedding、向量检索或模型可自行查询数据库的工具。服务端目前没有从账户数据库重建来源，确认状态和证据有效性主要依赖本地客户端；这与仅限本地的定位相适应，不能直接当作生产级信任边界。

界面告知会使用画像和目标，但没有自动展示“这一条回复实际发送了哪些洞察”的精确列表。模型被要求必要时说明依据，并不保证每次回复都能逐项解释参考内容。

## 9. Supabase 账户、数据库与备份

### 9.1 已有实现

- 使用 `@supabase/ssr` 创建浏览器和服务端客户端。
- 邮箱与密码注册、登录、退出；注册发送验证邮件。
- `/auth/callback` 使用回调 code 交换登录会话，随后跳转账户页。
- `src/proxy.ts` 仅匹配账户和 Auth 路径，用于会话刷新，没有给三个 AI 接口加入账户鉴权。
- 手动上传、读取和恢复 `user_snapshots`；备份操作前重新检查登录用户。
- 每个账户目前保存一份快照，下一次备份覆盖上一份，没有多版本备份历史。
- 备份包含聊天、画像、目标、人工整理和行动反馈；**不包含自动整理设置/检查点、旧决策演示数据或 AI 临时观察草稿**。
- UI 检查单次备份 JSON 为 5,000,000 字节上限；数据库也有 JSONB 大小约束。
- 恢复前会提示覆盖本地资料，先完整校验数据，再逐模块写入；写入失败时尝试回滚，回滚失败则明确提示。
- 支持下载本地 JSON 备份；当前没有从本地 JSON 文件导入的界面。
- 备份和恢复均是用户主动操作，不逐条实时同步、不自动上传。

`database/schema.sql` 定义了以下表：

| 表 | 设计用途 | 当前日常应用读写 |
| --- | --- | --- |
| `conversations` | 账户隔离的对话 | 仍在本地 store |
| `messages` | 消息及其顺序 | 仍在本地 store |
| `profile_insights` | 七维洞察与审核状态 | 仍在本地 store |
| `insight_evidence` | 洞察引用原文 | 仍在本地 store |

SQL 对十张表启用 RLS（Row Level Security，行级安全），为 `authenticated` 定义按 `auth.uid() = user_id` 的读取、插入、更新、删除规则，并限制未登录的 `anon`；部分关联使用带用户 ID 的组合外键防止跨账户关联。

源码中的这些规则说明了设计与代码边界，不等于本轮已经执行了真实双账户隔离测试。既有 README 记载：专用 Supabase 项目 `Zhiheng` 位于新加坡，表结构已应用；本轮没有在线重新验证，也没有重复执行建表 SQL。

### 9.3 验证状态与剩余问题

- 既有记录称 2026 年 9 月 30 日已确认一个真实注册账户完成邮箱验证。
- 邮件回调自动登录、真实账户备份恢复、另一浏览器或另一设备恢复及双账户隔离仍需端到端验证。
- 手机访问邮件里的 `localhost / 127.0.0.1` 指向手机自身，可能无法打开电脑上的原型；PKCE 自动回调也依赖发起流程的浏览器环境。验证成功后可回电脑用邮箱密码登录。
- 账户退出不会清理本地聊天；云端有账户隔离，本地工作副本仍按浏览器而非账户区分。
- 正规化表结构已经设计，但逐条数据库读写、迁移、同步冲突和删除传播尚未完成。
- 本地删除不会自动修改上一份云端快照，用户下一次主动备份才会覆盖云端旧资料。
- SQL 为洞察证据保留没有直接绑定消息/对话外键的来源 ID；本地删除对话则直接清理相关洞察。以后迁移时需要统一“删除洞察”与“保留但失效”的规则。

## 10. 隐私、用户控制与实际限制

- API Key 只通过服务端 `LLM_API_KEY` 使用，不放在 `NEXT_PUBLIC_` 变量中；`.env.local` 被 Git 忽略。
- Supabase 浏览器只使用项目 URL 和 publishable key，不应放入 service role key。
- 数据本地保存不等于全部离线：聊天请求会把近期对话、选中的确认画像和启用目标发给 DeepSeek；提取和观察各有自己的发送范围。界面已说明这些使用范围。
- 云端备份包含聊天原文与画像依据，由用户主动决定上传；登录本身不自动上传。
- 用户可以修改、驳回和删除洞察，模型不会自动覆盖审核结果。
- 浏览器 localStorage 和导出的 JSON 没有在应用层加密。它们不能被描述为安全的私密云账户存储或端到端加密。
- 本地多个 key 的跨模块操作不具有数据库事务能力；快照恢复有尝试回滚，但普通删除和重置仍可能部分成功。
- 候选的原话引用可验证，描述是否忠实、是否把一次事件泛化，仍依赖用户审核和模型质量。
- 当前不做心理诊断，不提供未经定义的人格百分比，也没有长期效果验证。

## 11. 旧方案保留了什么

旧主线是“历史决策 → 候选行为模式 → 用户确认 → 改进目标 → 三视角建议 → 反馈”，设计过普通 AI、Original Me 和 Better Me 三个上下文。

当前仓库仍保留：

- `src/types/domain.ts` 中的 `DecisionCase`、`BehaviorPattern`、`ImprovementGoal`、`DecisionComparison`、`DecisionFeedback` 等类型。
- `src/types/api.ts` 中旧分析与对比接口契约；这些类型不代表对应旧 API 已接通。
- `src/lib/data` 的合成 fixture、结构校验、本地数据入口与状态联动。

### 13.4 建议人工验收

1. 在专用浏览器用合成资料创建对话，检查刷新后消息保留。
2. 提取候选，核对读取范围、消息 ID 和原话，不强求模型固定输出某句话。
3. 确认一条，修改另一条并观察重新审核，驳回不准确判断；检查候选和驳回内容不进入当前画像。
4. 每维填写一个目标、选择意愿并暂停；修改暂停目标后确认仍暂停。
5. 新建对话，检查回复参考有效画像与启用目标；暂停目标不参与请求。
6. 删除源对话，确认对应洞察清理或失效，后续聊天不再使用。
7. 开启持续整理，在起点之后发出四条用户消息，检查候选仍需审核；关闭后不触发。
8. 生成观察草稿，核对关联洞察；刷新后草稿不作为事实保存。
9. 记录合成行动，编辑目标后查看历史记录仍保留旧文字；至少六条后检查分类比较。
10. 另用测试账户验证注册、邮件、登录、备份和另一浏览器恢复，并测试第二账户无法读取第一账户快照。覆盖操作前下载本地备份。

## 14. 当前设计的优点、问题与下一步

以下是依据当前代码作出的工程判断，不是用户研究或竞品结论。

### 14.1 值得保留的设计

- 主流程清楚：聊天、证据、审核、当前画像、目标、后续帮助可以形成可演示闭环。
- 用户审核是核心步骤，来源可以核对；修改会重新审核，驳回和无效来源不会进入正常聊天。
- 当前状态、目标、意愿与行动结果分别保存，避免把想要改变当作已经改变。
- 数据与组件分层，store 可以独立测试，依赖数量相对有限，适合继续小步开发。
- 配置和存储失败有明确提示，已有测试关注坏数据保留和恢复回滚。
- 对生产 AI、自动学习、诊断和效果的能力边界较明确。

### 14.2 优先关注的问题

| 优先顺序 | 问题 | 实际影响 |
| --- | --- | --- |
| 1 | 本地工作区有大量未提交新功能，文档状态不一致 | 其他成员与 AI 可能看到不同版本，误判实现或重复开发 |
| 2 | 账户备份恢复和真实隔离缺少完整实测 | 入口存在并不保证用户真正能跨浏览器恢复 |
| 3 | 本地资料未按账户分区 | 切换账号仍看见同一份本地资料，备份到哪个账户需要明确 |
| 4 | 生产 AI 接口关闭且未接账户授权/限流 | 当前适合本地演示，不能直接公开为多人服务 |
| 5 | 候选描述仍可能泛化或重复 | 原话是真的，判断仍可能不准确，审核负担会增长 |
| 6 | 长对话和大量洞察只做窗口截取、文字匹配 | 可能遗漏重要历史或发送关联较弱的信息 |
| 7 | 行动反馈未进入画像更新流程 | 有记录工具，但“用实际结果校准帮助”的闭环还未成立 |
| 8 | 目标修改仍共用 ID，画像缺少时间和完整审核轨迹 | 近期比较可能混合目标版本，长期变化难以解释 |
| 9 | 本地跨模块清理与云端删除规则尚未统一 | 迁移后可能出现残留引用、旧快照或不同删除语义 |
| 10 | 旧演示与新主流程仍有部分代码耦合 | 维护者需要辨别两套类型、目标和存储入口 |

### 14.3 建议下一轮只做的小目标

1. **先对齐版本和事实。** 审查未提交改动、同步主要文档，按协作规则通过 PR 交付；确认其他成员使用的是同一个功能版本。
2. **走通真实备份恢复。** 以测试资料验证两浏览器、两账户、覆盖、坏快照和失败保留，记录证据；明确本地账号切换行为。
3. **改善最常见的审核问题。** 使用少量合成案例检查泛化、重复、错误来源和用户纠正，不先堆更复杂的 AI 系统。
4. **再选一个目标做反馈闭环。** 明确目标版本，用户如何用一次实际结果修正候选、何时确认；不能让自评自动改写事实。
5. **需要公开服务时再接完整服务端边界。** 账户鉴权、服务端读取所属资料、用量限制和错误处理应一起验收，再开放生产模型接口。
6. 数据增长造成可复现问题后，再评估摘要、语义检索、正规化实时同步等优化。正式 UI 由曹根据已有数据契约设计。
